# 同一个轮腿控制器，比较共享动作与独立动作

旧的“两维与八维”实验同时换了低层控制器，结果不能只归因于动作维数。这一轮让两个策略都使用同一套轮腿控制：只改变策略能独立调节哪些动作。先读[主线控制与学习](locomotion_lab.md)，再看这里的映射和对照条件。

正式六模型对照已完成，逐种子指标见[结果报告](../results/d1_shared_action_study/README.md)。八维策略在两个训练种子的留出速度误差上低于共享策略，另一个种子更高；与零残差相比也有高度、姿态和机械活动量的代价。下面先解释这个比较实际控制了哪些条件。

## 两种策略实际能控制什么

物理动作始终是八个归一化修正量：前四个分别调整四腿伸缩参考，后四个分别调整四轮速度参考。动作顺序由原轮腿控制器定义，量纲换算也由它完成。

| 模式 | 策略输出 | 送给低层控制器的八维动作 |
|---|---|---|
| `shared2` | `[a_leg, a_wheel]` | `[a_leg, a_leg, a_leg, a_leg, a_wheel, a_wheel, a_wheel, a_wheel]` |
| `independent8` | 八个独立坐标 | 原样传递 |

低层会把归一化动作限幅到 `[-1,1]`，腿伸缩修正乘 `0.04 m`，轮速修正乘 `4 rad/s`，随后仍受原有机械范围和控制限值约束。比如 `[0.25,-0.5]` 对应每腿 `+0.01 m` 的参考修正和每轮 `-2 rad/s` 的速度修正；不是立即把腿移动 1 cm，也不是轮子必然达到该速度。

共享策略仍能转向，因为基线控制器会根据 yaw 命令产生左右轮差速。它缺少的是逐轮、逐腿独立残差，不能将 `shared2` 描述为“只会直行”。

映射在 [locomotion_env.py](../src/wheel_legged_control/d1/locomotion_env.py) 中发生，低层 [wheel_leg_controller.py](../src/wheel_legged_control/d1/wheel_leg_controller.py) 没有为共享模式另开一套控制逻辑。两模式都保留 82 维单帧观测；其中上次物理动作仍占八维，不能为了配合二输出策略而删成两维。

[对应测试](../tests/test_d1_shared_actions.py)不只检查数组形状：把同一二元动作广播后送入八维环境，逐拍比较状态、观测、奖励与力矩。零动作、非零动作、限幅和延迟条件均检查等价。这个等价性针对给定的同一动作序列，不表示分别训练的两个策略会产生相同轨迹。

## PPO 的概率应当算几维

训练时有三个不同的对象：策略采样的高斯动作 `u`、经过动作空间裁剪的策略动作 `a=clip(u,-1,1)`、广播到物理通道的动作 `b`。环境收到的是 `a`，PPO 保存的旧 log probability 对应 `u`。

对于对角高斯策略：

$$
\log\pi(u\mid s)=-\frac12\sum_{i=1}^{d}
\left[\left(\frac{u_i-\mu_i(s)}{\sigma_i}\right)^2+2\log\sigma_i+\log(2\pi)\right].
$$

`shared2` 的求和上限是 2。不能把两个样本各复制四遍，再当作八次独立采样计算概率。四腿组内完全相关，四轮组内也完全相关；八个坐标仅由两个随机量决定，在八维空间中没有普通的独立高斯密度。

手算取 `μ=[0,0]、σ=[1,1]、u=[0,0]`，得到 `log π=-log(2π)≈-1.837877`。若错误复制成八个独立标准高斯，会得到约 `-7.351508`。旧、新策略概率比的指数也会因此改变，PPO 裁剪目标随之算错。接着可用[数值 PPO 练习](ppo_learning_lab.md)与[一次参数更新](ppo_update_lab.md)检查比率、优势符号和梯度。

记录中的字段按所在文件区分：

| 记录 | 策略动作 | 物理动作 |
|---|---|---|
| 训练采样 CSV | `raw_action_i` 是未裁剪高斯；`applied_action_i` 是裁剪后的策略动作 | `physical_applied_action_i` 是环境返回的物理动作，不改变旧列含义 |
| 评测 NPZ | `actions` / `policy_actions` 是确定性策略输出，宽度为 2 或 8 | `physical_actions` 宽度恒为 8 |
| 键盘/回放 NPZ | `policy_action` 是环境收到的策略动作 | `raw_action` / `applied_action` 保持原物理通道含义 |

动作惩罚和评测动作均方使用实际八维物理动作。PPO 的概率、熵和输出层参数量则使用策略维度。这两种统计目的不同，不应统一成一个模糊的“动作大小”。

共享模式的两个坐标各复制四次，所以归一化均方不变：`mean([0.25,-0.5]²)=0.15625`，广播后的八维均方也是 `0.15625`。这只能检查动作统计的归一化；腿伸缩和轮速的单位不同，该数值没有能量单位，也不能推断两种策略的实际机械功率相同。

## 固定哪些条件，仍有哪些差异

两组共用以下条件：

- 轮腿低层、奖励、物理动作尺度、初始条件与终止规则。
- `imu_encoder_fusion` 状态源，单帧 82 维观测，测量延迟为零，不做域随机化。
- 五项反馈参数为 `wheel_kp=0.55`、`wheel_ki=1.5`、`yaw_feedback_gain=4`、`leg_feedback_scale=1`、`attitude_feedback_scale=0.25`。
- 每模式三个训练种子 `31000/32000/33000`，每模型 32768 次环境转移，四个并行环境；合计 196608 次转移。一次环境转移对应一次 10 ms 控制拍，不是一次 2 ms 物理积分。
- 相同的 PPO 隐层和训练设置，每轮每环境采集 128 步，四环境共 512 个样本。只保存并评测固定预算结束时的模型，不按开发集或留出集选最佳 checkpoint。

“同一随机种子”也不保证经历相同状态：动作形状改变会影响随机采样，行为又影响终止和重置时刻。因此三个训练种子是有限的重复实验，不能把每个控制拍当成独立统计样本。

八维策略还多了输出层权重和 log standard deviation 参数，共享动作的物理相关结构也不同。这是动作结构对照，不是严格只改变一个标量的实验。报告应列实际网络参数量，而不是说“两组网络完全相同”。

实际训练记录的总参数量为共享模式 19141、独立模式 19537。差出的 396 项来自六个额外输出坐标，每个坐标增加 64 个输出权重、1 个偏置和 1 个 log standard deviation 参数，即 `6×(64+1+1)=396`；隐层和价值网络不变。

## 地形和评测怎么配对

新套件 `action_compare_v1` 复用原训练的四条道路；开发集和留出集使用另定的坡度、横坡、波纹与台阶参数实例。开发集仍属 `right_offset` 布局，留出集仍属 `s_bend/diagonal` 布局，命令脚本也复用已有开发/留出任务。这里没有引入新地形布局族，更没有证明任意地形泛化。

每模型评测两个 split，各含两道路 × 两个 episode reset 种子。开发种子为 `1017/1029`，留出为 `1617/1629`；实际传感器 `measurement_seed` 由重置过程抽样并另行记录、核对。同一案例的道路、命令、测量噪声种子与低层参数必须一致；训练种子只标识模型，不代替评测种子。

零残差基线每个 split 只跑一份四案例结果，各模型与它配对。不能重复抄三份零策略结果，再称为三个独立训练重复。全研究为六次训练、十二次策略评测和两次零策略评测，共 20 条命令、48 个策略案例和 8 个零策略案例。

## 从接口检查到正式实验

按 [README](../README.md) 安装依赖后，在仓库根目录先运行：

```bash
python scripts/run_d1_shared_action_study.py --smoke \
  --output results/my_shared_action_smoke
```

Smoke 只训练两个 512 步模型，回合上限 0.2 s，检查两种接口、保存、重载和评测记录。机器人基本还没进入运动任务，不能从这个结果比较跟踪性能。

接口验证完成后，固定预算的正式命令为：

```bash
python scripts/run_d1_shared_action_study.py \
  --output results/my_shared_action_study

python scripts/analyze_d1_shared_actions.py results/my_shared_action_study \
  --output results/my_shared_action_analysis
```

目录必须不存在。调度器先写完整协议，逐个串行启动任务，所有开发评测完成后才进入留出；每条命令前后都检查源码。某条命令报错或源码改变就停止并保留现场，不自动跳过失败。`commands_completed` 只表示命令结束，不代表质量达标。

分析器不加载模型、不调用仿真或训练库，从已有记录复算轨迹指标、动作映射、配对条件和 PPO 数学记录。模型文件只检查哈希，不做反序列化。实际模型重载由前面的评测命令验证；只加载自己生成或信任的模型。

每个正式模型包含 `32768/(4×128)=64` 次 PPO `train()` 调用。每次调用记录更新前后的数值，独立复算其中按 env-major 排列的前 128 个样本；六模型对应 384 份记录。它们不是 384 个独立训练重复，也不等于复演了全部 minibatch 梯度步骤。记录里的原始优势裁剪样例与训练时按 minibatch 归一化优势的损失也要分开。

训练完成后，共享策略也可以接到共用运行入口。以下用你自己的输出路径，先做无窗口的 0.2 s 接口检查：

```bash
python scripts/run_d1_locomotion.py --source sensor --seconds 0.2 \
  --action-mode shared2 --terrain-suite action_compare_v1 \
  --terrain development --terrain-index 0 --seed 1017 \
  --wheel-kp 0.55 --wheel-ki 1.5 --yaw-feedback-gain 4 \
  --leg-feedback-scale 1 --attitude-feedback-scale 0.25 \
  --policy results/my_shared_action_study/shared2_seed31000/checkpoint.zip \
  --metadata results/my_shared_action_study/shared2_seed31000/checkpoint.json \
  --output results/my_shared_interface_check
```

有桌面显示时可换一个新输出目录，添加 `--keyboard`、把 `--seconds` 调大，交互键位沿用主线说明。这里的短跑和自动化测试不等于人工键盘验收。加载独立策略时同时改动作模式与模型路径；不要手改 sidecar 把二输出模型伪装成八输出模型。

## 怎样读到一个站得住的结论

先报告每个训练种子的完成数、质量达标数、全部终止原因和实际时长，再看误差。提前摔倒的两秒记录，不能凭较低 RMSE 赢过完整六十秒记录。

只有双方都完成且时长相等的配对案例才计算指标差。完成案例均值要和失败数一起阅读；如果一个模式把困难案例都提前摔掉，幸存案例均值可能显得很好。还需同时看速度、yaw、高度、姿态、机械功率和地形曝光，不能用单一速度指标概括整体优劣。

可以先写下自己的预测，再看结果：共享动作是否更容易在小预算下学会不扰乱低层？独立残差是否在横坡上更有用，还是增加了探索干扰？要回答这些问题，需要完整逐种子结果，而不是“八维更高级”的预设。

即使所有留出案例完成，这仍是有限仿真设置下的结果；这里没有真机训练、真实执行器辨识或硬件安全验证。

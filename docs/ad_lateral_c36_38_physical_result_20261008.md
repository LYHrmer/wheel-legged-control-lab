# C36–C38：对角两支撑门禁修正的物理验证、潜伏缺陷与独立审计闭环

本文记录三次连续的单次有界物理运行。三次都**没有完成任何一次双腿交换**，但每次都停在一个明确、已定位的原因上，而不是重复同一个失败。**零训练，零新策略，零优化器步。** 三份 GO 均由 root 签署，显式标注 `astra_reviewed: false`；Astra 终审通道在本终端不可用，未被冒称使用。

## 背景

[C35 结果与定位](ad_lateral_pair_feasibility_20261004.md)指出两份冻结 clarification 互斥：`clarifications35_01` 要求 `transfer` 相位全程四轮载荷严格为正，`clarifications35_03` 却要求同一相位把摆动组权重在 0.06 s 内归零到零载荷。C35 在 transfer 历时 0.05 s 时撞上这个互斥而终止，从未进入两支撑。

[横移步态方案重审](ad_lateral_gait_review_20261004.md)据此推断"该步态在冻结标称蹲姿下静力不成立"（COM 相对接触矩形中心前移 21.7 mm，缺口 1.34–1.38 倍）。C36–C38 是对这个推断的物理检验。

## C36：pre-unload 支撑门禁修正，物理证实

**修正**（`continuation36/sol36/core36.py` + `adapter36.py`，10 项纯测试先行）：把 `transfer` 相位按摆动组权重是否已降到 0.5 以下分成两段——前段维持冻结的全四轮要求，后段改为与冻结空中相位同样严格的"支撑对"要求（每个支撑轮独立正载荷、支撑对法向和 ≥0.5mg）。边界取自设计自身的权重斜坡，在 `elapsed=0.03 s` 处精确过 0.5。原生守卫代码**一字节未改**——它只根据声明的 `support_mode` 选择区间。

**结果**：205 个控制步、1025 个 native 子步，**零原生安全违规**。在 native 1020——C35 死亡的同一个子步同一个状态——摆动轮 3 载荷降到精确 0 N，而支撑对（轮 1、2）承担 458.6 N，远超 236.2 N 的要求，门禁通过。运行继续越过 transfer，进入 lift 相位，撞上一个继承的潜伏缺陷：`runtime35.py` 的 `fullM` 静态查询检查无条件引用了 MuJoCo 3.12 已不存在的 `MjData.qM` 属性。C35 自己的账本记录 `fullM: 0`——它从未进入需要耦合惯量的相位，这个缺陷在这个代码库里潜伏了一整个 contract。

## C37：修复潜伏缺陷，物理证实两支撑成立，定位真正的阻塞

**修复**（`continuation37/root37/runtime37.py`，7 项纯测试）：把判定短路化，`modern` 分支为真时完全不触碰 `.qM`，其余语义逐字节保持冻结行为（含一项直接断言"冻结表达式在真实输入上确实会抛异常"）。

**结果**：299 个控制步、1495 个 native 子步，**零原生安全违规**。完整走过 transfer → lift → horizontal → lower → probe → dwell。

| 量 | 实测 | 门限 |
|---|---:|---:|
| 两支撑（pair 区间）native 子步 | **485**（≈0.97 s） | — |
| 支撑对法向和 最小值 | **343.5 N** | 236.2 N（余量 45%） |
| 单支撑轮载荷 最小值 | **140.9 N** | >1e-8 N |
| 气相最大 \|roll\| / \|pitch\| | **4.15° / 4.03°** | 18.33° |

**[重审文档](ad_lateral_gait_review_20261004.md)"静力不成立"的预测被物理否证**——接触斑力矩容量按两个保存接触槽估出的 ±12.42 mm 严重低估，而该推断显式排除了姿态反馈，控制器实际在动态维持姿态。

真正的阻塞是 `touchdown_dwell_timeout`。从保存证据提取的[翘板诊断](../results/d1_ad_velocity_reference_20261003/continuation36_38/continuation37/rocking_diagnosis_37.json)（[提取脚本](../results/d1_ad_velocity_reference_20261003/continuation36_38/publication_tools/extract_rocking_diagnosis_37.py)，对同一份密封 native 记录的独立重算）：

- probe+dwell 共 300 个 native 子步，**两个返回轮同时接触的只有 4 个**
- 气相姿态持续非零偏置：roll 均值 −1.13°，pitch 均值 +1.02°
- 两返回轮净空高差峰峰 **67.76 mm**，跨 594.3 mm 间距对应绕支撑对角线 **5.12°** 转动，与实测 4.15° 姿态偏移量级一致

机理：COM 前移使两条对角线都不过 COM；绕某条对角线的转动把其中一个返回轮抬高、另一个压低，两者交替触地，永远凑不满连续 0.08 s 的 dwell。**这是原静力推断的机理本身是对的，表现形式不同**——不是倾倒失稳，是振荡不触地。

C37 的第二个发现：独立验收器（`read35.py`）拒绝读取结果——它硬编码了 C35 合同字面量、"transfer 恒为全四轮"假设、以及 5 用例预算上限，三处都是 C35 时代遗留，不认识 C36/37 的新语义。

## C38：修复记录语义，完成独立审计

C37 的记录语义本身也有一个缺陷：`adapter36` 在 pre-unload 窗口把 `swing_legs` 填成摆动对以让守卫看到支撑对，但验收器的交叉校验是 `fullM 调用数 == bool(swing_legs)`，而 transfer 期间不计算耦合惯量，0 ≠ 1。**修正**（`continuation38/sol38/adapter38.py`，6 项纯测试）：只声明 `support_mode`/`stance_legs`，`swing_legs` 保持冻结的空值。

**确定性校验**：C38 与 C37 的 1495 行 native 记录逐行 `qpos`/`qvel` 完全相同——记录语义修复没有产生任何物理副作用，和承诺的一样。

随后扩展独立验收器以认识新语义（全部先纯测试、再用真实数据验证）：
- `native_read38.py`：把相位/支撑掩码的期望值扩展到 pre-unload 窗口，边界常数从 `core36.PREUNLOAD_ELAPSED36` **导入而非重抄**，8 项纯测试
- `ledger_read38.py`：把预测调用上限从硬编码的 `3001`（5 用例）泛化为 `len(cases)×(prepare+retention)+1`，纯测试确认 5 用例时精确退化为原字面量 `3001`/`3032`

**最终结果：`exit_code=0`，`ledger.passed=true`，`native_checked=1495`**（含 94 次 fullM 调用）——C36–C38 investigation 的第一次完整独立审计闭环。`uncompleted_requirements` 列出的 `all4_stop`/`400_B22_retention`/`complete_native_case` 是物理上真实未完成（因 timeout 中止），不是审计缺陷。

## 一处需要更正的早期设计结论

[重审文档第 9 节](ad_lateral_gait_review_20261004.md)曾称姿态过渡只需 0.0172 s，"远在准备窗口之内"——该数字只核对了参考速度限幅，没有核对动态力矩。[精确推导](../results/d1_ad_velocity_reference_20261003/review_20261004/wheel_roll_compensation_20261008.py)用 URDF 精确轮惯量（`I_zz=0.007609 kg·m²`）复算：0.0172 s 时腿需要约 296 N·m（超 80 N·m 限幅 3.7 倍）、轮需要约 30 N·m（超 12 N·m 限幅 2.5 倍），**两者都不可行**。精确力矩约束下的最小时长是 **0.0374 s**（腿侧更紧），取 0.1 s 留出余量，仍远在 200 控制步（2 s）准备窗口之内。已在重审文档、交接文档与本目录 README 三处更正。

## 下一步：一个比预期更大的架构缺口

对齐蹲姿修法本身没有变——标称 thigh 0.800 → 命令 0.7524、calf → −1.502261，让 COM 精确落在两条对角线上。但**它不能实现为"改几个参考数字"**：现有 `compute()` 的全部力矩路径都是从脚端笛卡尔目标反解 IK 得到关节角；对齐蹲姿需要的是**直接在关节空间驱动 thigh/calf**（绕开 IK），同时让轮子滚动抵消脚端的隐含位移（已验证的滚动量 0.2934 rad/腿），这是两条不同的控制路径，需要在状态机里插入一个全新的子相位，有自己的参考律、自己的纯测试、自己的合同——不是对现有相位的参数调整。

这个架构识别本身是本轮分析最重要的产出之一：如果不先认清这一点就仓促写代码，很可能在架构层面出错，而错误只会在物理仿真里才暴露，浪费下一次有界物理尝试。这个新子相位的设计、实现、验证留作独立的下一步（C39），不在本轮勉强交付。

## 2. 预先排序的五个可证伪假设

这些均为待检验假设；相关性、训练覆盖或算术重放均不单独证明动力学因果。

| 排序 / 假设 | 若假设成立，应看到什么 | 使假设减弱或否定的证据 | 最小后续区分手段 |
|---|---|---|---|
| H1：学习残差的左右轮差分或腿姿偏置干扰 yaw | 两学习臂在对应符号/换向子段存在有效差分残差、腿偏移或力矩不对称，并与新增 yaw 误差同段出现；原始动作到实际执行的链可说明偏置未被 gate/限幅消除 | 实际执行残差在相关通道近零，或误差完全发生于残差偏置前且无一致方向；纯算术重放不能产生预期方向的控制变化 | 固定 checkpoint、保留全部 RL 通道，针对被定位控制缺口的单一反馈/映射修复；通道消融若另行采用只能作机制诊断，不能取得任务资格 |
| H2：yaw 现有反馈的有效请求限幅或名义差动目标到真实 yaw 的动态跟踪缺口，在腿姿/轮载荷改变后被放大 | zero 也在同类 servo 换向段贡献大量 SSE；现有 effective yaw 触及±0.6，或实际 yaw、轮速、载荷/保护有明显滞后/不对称；学习残差可能抵消该反馈 | 误差主要为稳定平台上仅学习臂出现的恒定偏差，且无反馈限幅/动态响应缺口；或发现更直接的命令/坐标错误 | 只修改已存在 yaw 闭环中被定位的一个环节；不以“缺少 yaw 反馈”作为修复理由，与 H1 分清作用点 |
| H3：坡道轮 PI 的共同积分保留/饱和处理导致速度正偏差 | 坡段中共同积分建立为正，在 hold 或离坡后仍推动正偏；COM 超速时总 common 请求仍偏正；检查 pre-common PI antiwindup 与最终保护是否脱节 | 三臂积分不呈共同正偏，或积分变化无法解释超速段，或误差先于积分建立且明显由参考语义引起 | 只改经定位的共同速度积分/antiwindup 环节；轮差分、姿态支撑、奖励与 RL 输入保持冻结 |
| H4：用于反馈的速度与任务评分速度或名义轮速参考存在语义/坐标偏差 | `consumed_body_com_forward_mps`、控制前状态速度、评分 post COM body vx 与命令在相同状态下有可解释的系统差异，或坡道名义轮速本身隐含更高的 COM 参考；差异与超速大小相当 | 查明二者是同一物理点/坐标，仅有合法 pre/post 时间差；残差不足以解释偏差 | 修正被证实的单位、物理点或映射；不得将评分改为较容易通过的速度定义 |
| H5：新增训练的实际命令/地形覆盖不足，使已有失配没有被学习修正 | 高速与大幅双向 yaw 的联合有效暴露少，坡道几何后程/完整离坡阶段在实际完成训练行中缺失；误差集中于这些缺口 | 两臂在相关联合工况有充分实际控制行和反复访问，且失败集中于已覆盖区域；或明确控制实现缺陷已足够解释 | 只有前四项没有足够低风险控制修复时，才另冻一次有界、单因素覆盖干预训练；不直接追加长训练 |

H4 特别核对：控制 adapter 传入纯函数的字段名是 `body_com_forward_mps`，表达式为 `state.base_linear_velocity_body[0]`。字段名本身不是错误证据；先追溯状态定义及实际保存值，区分 base 原点、COM 与 pre/post 时刻。

已有源码还明确：nominal yaw 采用 `clip(servo_yaw + 4*(servo_yaw-estimated_body_yaw), ±0.6)`，不是开环 yaw。限幅前的四轮平均请求将 wheel P 与 common P 合并后为 `2.2*(mean(nominal_wheel + policy_wheel_offset)-body_forward/0.087) + mean(wheel_integral)`；因此完整控制器已有 COM 速度比例反馈。积分仍由 target 减实际 wheel omega 推进，这种反馈与积分误差定义的差异需要保存数据检验，不能误述为“没有速度反馈”。

## 3. 阶段 A：保存数据诊断，零模型、零物理

输入范围仅限：C16 中两故障任务各三臂的六场既存 control/state/schedule/geometry/native 归档；C15 两臂全部已完成的 16×1,024 numeric 行及对应实际 episode schedules/receipts；需要解释字段时读取被冻结的纯控制/命令/观测源。其他四项通过任务只在定位跨工况参考偏差或准备回归时读取所需保存字段，不重新评分全部旧批次。读取源文件、哈希、gzip/JSON/NPZ 数值解析不构造环境、不导入 Torch/SB3/MuJoCo/engine binding、不反序列化 ZIP/torch checkpoint。

root 在洁净进程运行一个可复现命令生成 `diagnosis_17.json` 和简短中文结论，记录输入/脚本 hash、耗时、字段缺口。该命令必须从保存值重现上述 yaw 与 ramp 的失败门，形成可见的红信号；这是保存记录重放，不冒充执行了未来修复后的实际控制路径。历史输入不变，旧失败自然保持为失败；修复验收读新归档。

### A1. 对齐和最小分段

- 用控制记录 tick 对齐本 tick 实际消费的 servo 命令、pre-state、policy action、最终扭矩与下一 post-state；不混用 qpos/qvel[k] 与 [k+1]。主要 yaw 误差为 post body yaw rate 减去 consumed servo yaw，vx 同理；raw 误差仅作命令说明。
- yaw 原 hold 固定 `[415,815)`，raw 子段 `[415,515)`、`[515,715)`、`[715,815)`，完整 drive 仍 `[175,815)`。各子段同时按保存 servo 是否到达当前 raw yaw 分成 transition/plateau；阈值只用于诊断分类，不能排除正式计分行。servo yaw ±0.006/tick，故从 +0.3 到 −0.3 约需100步，不用任意短瞬态窗排掉换向误差。
- 每臂每段给出 n、有符号均误差、RMS、SSE 及全 hold SSE 比例、最大误差；正/负命令分别列出。任何额外峰值片段标为探索性，不把它追认成预注册主要窗口。
- ramp 原 hold 固定 `[600,1000)`、drive `[175,1355)`、final `[1700,1800)`。先报固定 hold 四个100步子段，再用真实已存 positive wheel contactForce 按 approach/up/deck/down/cleared 与混合接触作互斥标注；混合接触不强行归到一个坡面，未存足够几何则标不可判定。保持正式窗口不随接触时刻移动。

### A2. 控制量与覆盖

从 `controller_record.calculation` 检查 raw/clipped/applied action、leg/wheel offsets、nominal/最终目标、轮速误差、integral before/after、commit mask、base wheel torque、common wheel-P、final/safe torque 及保护占比。先从冻结 nominal 映射确定 FL/FR/RL/RR、轮方向和差动正号，再定义 common=四轮平均、left/right 与 yaw differential；不得仅凭数组位置猜符号。腿关节12通道与轮速4通道分别列出。

仅在记录已含全部所需输入时，允许 root 用纯算术重放原 `compute_residual16` 核对已存输出或计算同一个保存状态下的控制增量；该操作 0 模型/0 物理，使用导入禁止保护。重放改变 action/参数产生的扭矩只是**即时控制算术对照**，不能当成反事实 yaw/vx 轨迹、能耗、稳定性或最终任务成功。各策略状态已分叉，三臂逐 tick 差不能解释成同状态消融。

训练覆盖以已完成 numeric 行为准，不把 schedule 的未执行尾段算作暴露。每臂报告实际 episode/terrain/command 表，分别统计 raw/servo 的 vx、|yaw|、符号及两者联合；明确 exact formal 点 `(1.2, ±0.3)`、邻域 `vx≥1.1 且 |servo yaw|≥0.25`，两阈值在读取分布前冻结。坡道报告有效 drive、hold-like steady-speed、up/deck/down/cleared 的可得计数及完整回合终止原因。不给“充分覆盖”任意二元门，报告数值并据此削弱或支持 H5。

### A3. 阶段 A 出口

## 4. 阶段 B：按证据选择最小干预并完成开发验证

优先能解释已见误差的最小控制修复，不把 H5 自动升级为训练理由。每个候选只改变一个已命名因素：修复 yaw 时不同时动坡道速度环、reward 或 clip；修复 ramp 时不同时动 yaw、动作幅值或课程。固定 RL 模型与全部16动作通道保持运行。若两因素都需要，先分别建立定向开发证据，再冻结二者组合；验收必须测试组合后的实际执行。若一个共享反馈/坐标错误同时解释二者，可只改该一个因素，并保留两任务分别的证据。

物理开发首批建议仅包括所需低速 floor、yaw 与 ramp 完整脚本；保留原 full horizon 才能检验停止和清除，不能用 hold 末尾截断获得通过。使用新的明确标记为 development 的 seed/场次；不得重放已完成 C16 场次并称为新独立证据。原 C16 数据可作为历史描述，新的因果对照需同一批次匹配初态及唯一差异。

短附录必须列出 cold worker 数、各 worker 控制上限、5×normal native、compiler 构造上限、策略 load/probe/predict rows、优化器/训练上限、soft/close/hard 时间、归档与 reader 子进程归属及清理。沿用 C16 cold owner、archive13 原子事务、clean reader、实际 C/Python/native/controller/contactForce 链与前后同集 hash。开发/资格每个 reservation 独占文件且失败不退款、不原位重试；修复工程失败后若需要新尝试，用新的明确 reservation，不改旧失败。

## 5. 阶段 C：固定组合后的独立资格验收

候选在开发脚本通过后冻结唯一源码/模型组合、reader与正式 seeds，再执行资格。已用于调参/选择的所有场次只叫开发，不叫 heldout。资格 seeds 必须在该阶段任何物理执行前写入合同并核查未用；为暴露转向非对称，除原正→负→正模式外必须含预先冻结的负→正→负镜像 yaw。镜像保留相同 |yaw|、servo slew、时长、速度及门，不在看到误差后选方向。

最低验收结构为：一个新的六任务成套 seed 组，加一个独立 seed 的原 yaw、镜像 yaw 与完整 ramp；具体场次/精确上界由 C 短附录在首个资格执行前冻结。六任务基础模式/窗口沿用 C15（每套 9,800 controls），附加 yaw/ramp 分别1,600/1,800 controls。需要资格的每个学习配置先按 C16 floor 形式取得基础执行资格；floor仅提供继续运行许可。对照至少含**同一修复控制器下的 zero 与启用完整 RL 的唯一候选**；若要将收益归于控制修复，还需在开发批次保留旧控制器同批对照，不能用历史单 seed 充当配对因果证据。

全部正式场次按如下层级裁决，不能互相补偿：

1. 来源、完整记录、真实 controller/native/contactForce 链、计步、精确初态配对、warning/归档与独立 reader 通过。
2. 原全部安全、完整 horizon、最终停止、terrain channel、ramp 三几何正轮载荷与整轮清除门通过。
3. 原任务速度/yaw 门逐场通过；主要 yaw hold RMS≤0.12；ramp hold 均速落在[0.41,0.49]且 vx RMS≤0.05。其他四项门和高速要求不变，不能靠总体平均抵消一个失败 seed 或方向。
4. 明确验证学习策略全16动作通道确已执行：policy predict、raw/clipped/effective action、actual residual/torque映射闭合，raw motion期间没有新增的地形/任务识别关闭逻辑。正负方向和坡道均保留执行日志。非零不等于有益；只证明没有用关闭RL冒充完成。

**“转向、坡道跟踪完成”** 仅在冻结候选所有正式 yaw/ramp（含镜像与第二 seed）及六任务回归全部满足1–4后可写。zero 失败不自动阻止候选任务资格，但会按其实际失败保留；zero 通过也不代替候选通过。

**“整体 RL 贡献”另判**：在同一修复基控、同一资格脚本和配对初态上，继续报告原 drive SSE、逐任务/hold SSE 与力矩平方成本门，按 C15 定义逐套计算，附加任务另表报告。基控修复的收益不能归功于 RL；总体贡献失败时仍须写 false。任务完整通过并不自动取得 default GUI、实机或自由键盘资格；这些没有本轮专门验收便保持原边界。旧 final 未作本轮物理对照便不声称新配置超过旧 final。
